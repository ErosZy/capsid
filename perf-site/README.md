# Performance History Site

Static GitHub Pages site presenting the release-line benchmark record
(throughput, cold start, memory) for Capsid.

## Layout

- `index.html` — self-contained page (no external assets, hand-rolled SVG
  charts).
- `data.js` — generated by `bench/collect-perf-point.py`; one point per
  release line measurement with machine fingerprint and evidence digests.
  Append-only: historical points are never edited.

## Producing a data point

From a tagged, clean-tree Release build on the canonical benchmark machine:

```sh
# 1. fixtures (cold-start lane) + trusted bytecode
python3 bench/gen-cold-start-apps.py /tmp/cold-start-apps

# 2. cold-start + warm + PSS (capsid source/bytecode, node, deno, workerd)
ROUNDS=5 WARM=50 BUILD_DIR=build-release \
  WORKERD_BIN=/path/to/workerd \
  bash bench/cold-start.sh

# 3. QPS lane (capsid-host vs workerd vs node, frozen loadgen protocol)
OUT=<dir> HOST_BIN=build-release/capsid-host \
  WORKER=build-release/capsid-worker WORKERD_BIN=/path/to/workerd \
  bash bench/qps-lane.sh

# 4. merge into the site data
python3 bench/collect-perf-point.py \
  --cold-start <cold-start-out-dir> --qps <qps-out-dir> \
  --version "0.2.x" --release "v0.2.2"
```

## Publishing via GitHub Pages

The site deploys from `.github/workflows/perf-pages.yml` (artifact
deployment; no `gh-pages` branch). Enable it once:

Repository Settings → Pages → Build and deployment → Source:
**GitHub Actions**.

The workflow publishes the contents of `perf-site/` on every push to
`main` that touches the site or its data, and can be dispatched manually.

## Rules

1. Only measurements from tagged release builds on the canonical lane may
   become points; the fingerprint in each point makes the lane auditable.
2. `data.js` is append-only. Methodology changes bump the schema version
   and start a new series instead of rewriting history.
3. The raw result directories backing a point are preserved with their
   `sha256sums.txt` (referenced from the point's `evidence` map).

# Contributing Guide

Thank you for contributing to Capsid. The project is currently in the `0.1.x` stage, and the public ABI, security boundary, and behavioral contracts are still evolving quickly; a clearly scoped change with verifiable evidence matters more than the size of the change.

## Before You Begin

- For bugs, design suggestions, and compatibility questions, align scope first through a GitHub Issue.
- Do not disclose security vulnerabilities publicly; report them according to the [security policy](SECURITY.md).
- Large architectural changes, public ABI changes, or new escape-level capabilities should begin with a design discussion before implementation.
- Each Pull Request should address a single problem; do not include unrelated formatting or refactoring.

## Development Environment

Base dependencies include CMake 3.18+, a C/C++ toolchain, Node.js/npm, and OpenSSL. Building the first-party host also requires Boost; the full CI environment is defined by [`testing-validity.yml`](.github/workflows/testing-validity.yml).

```sh
git clone --recurse-submodules https://github.com/ErosZy/capsid.git
cd capsid
npm ci --ignore-scripts --prefix vendor/txiki.js

for directory in \
  examples/hono-reference \
  examples/itty-router-reference \
  examples/h3-v2-reference
do
  npm ci --ignore-scripts --prefix "$directory"
done
```

Day-to-day development build:

```sh
cmake -S . -B build \
  -DCMAKE_BUILD_TYPE=MinSizeRel \
  -DBUILD_TESTING=ON \
  -DCAPSID_BUILD_HOST=ON
cmake --build build --parallel
ctest --test-dir build --output-on-failure \
  -E '^wpt_conformance_not_configured$'
```

This command is not equivalent to full CI. For pinned WPT, sanitizer, fuzz, and privileged Linux sandbox validation, see [testing and continuous gates](docs/testing.md).

## Change Principles

### Code and Contracts

- Keep the C11 ABI and C++11 public wrappers usable; host-internal code may use the higher C++ standard declared by its target.
- New runtime behavior must have test coverage; when fixing regressions, add a minimal failing test first.
- Security decisions are fail-closed. Do not trade usability for silent degradation, and do not bypass capability, egress, sandbox, or artifact identity checks.
- Do not modify the generated working tree of `vendor/txiki.js`; vendored changes should enter through a reviewed patch and a locked identity flow.

### Documentation

The README maintains only positioning, the shortest onboarding path, security warnings, and stable entry points. The full set of fields, protocol details, test methodology, and performance evidence belongs in the corresponding authoritative `docs/` documents.

When facts conflict, resolve them in the following order:

1. Public headers, capability manifest, build configuration, and tests;
2. Raw test or benchmark artifacts generated by the current commit;
3. Markdown documentation.

Documentation changes require a synchronized check:

- Commands can be run from a clean checkout;
- Local relative links exist;
- New `docs/*.md` files are reachable from `docs/README.md`;
- Avoid copying test counts, status snapshots, or generated reports that become stale quickly;
- Behavior, configuration, or permission changes update all authoritative entry points.

You can run the documentation audit directly:

```sh
node tests/audit-current-docs.mjs .
```

## Pull Request Checklist

- [ ] The change has a single scope, and the commit message explains the “why”.
- [ ] New behavior or regression fixes have corresponding tests.
- [ ] Relevant local tests pass, and environment-gated checks that were not run are noted in the PR.
- [ ] Public ABI, configuration, permission, or platform contract changes are synchronized with the docs.
- [ ] No build directories, dependency directories, temporary profiles, or generated reports are committed.
- [ ] Performance claims include reproducible raw samples, environment, commands, correctness, and profile evidence.

Maintainers may ask you to split a change, add negative controls, or provide a minimal fixture that reproduces the result. CI results are one input to merging, but they do not replace human review of security boundaries and contract changes.

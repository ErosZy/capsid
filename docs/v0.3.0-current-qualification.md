## 本轮修复与验证

### 激活阶段 App 目录 FD 重复关闭

原诊断 [43423254468](https://github.com/ErosZy/capsid/actions/runs/43423254468)的25轮中24轮通过，`traced-7`保留真实 TSan 失败：部署线程关闭了被 Admin `accept()` 复用的 FD，Host退出66。`finish_activation()`借用部署操作持有的目录 FD，但 `PosixActiveStateFilesystem`析构先关闭它，调用方再次关闭；其他 syscall 记录也有同一目录连续两次关闭。

`src/host/managed_host.cc`现在区分适配器的拥有/借用模式：激活只借用，操作调用方仍负责一次终态关闭；退役、恢复、状态读取等原有调用方仍向适配器转移所有权。没有新增跨 worker 启动或回调的大锁，没有改变发布或回滚顺序，也没有扩大权限。

新增4项 Linux CTest，预算各30秒，覆盖首次部署、幂等回放、首次部署持久化失败和回放持久化失败。测试在第一次关闭时确定性复用同一 FD 为真实 Unix stream，要求精确一次关闭且新 stream 仍能传输。旧实现4/4失败，修复后4/4通过；最终项目级167项选集也包含这些测试。该证明解释了诊断中的重复关闭，不能据此把所有历史 `EPIPE/ECONNRESET` 都归为同一根因。

### Admin HTTP 增量解析

`src/host/admin_http.cc`保留 Beast 未消费的请求行、头部、chunk header及 trailer 字节；先校验头部 framing，再解析正文；畸形或超限输入直接返回，不继续读取或调用 backend。未完成 chunk extension 同样有存储上限。peer授权、原限额、绝对阶段期限和调用方 FD 所有权保持不变。

新增5项 Unix CTest，预算各10秒，覆盖逐字节头部、合并/分片 chunked 正文、错误拒绝、限额及缓冲边界。原组件旧实现16通过/5失败，修复后普通和 ASan+UBSan 组件各21/21通过；新增5项各重复10次全部通过。最终167项项目级选集包含这13项 HTTP和8项 Admin service 测试。组件依赖复用的限制仍保留，不冒充全依赖插桩接受。

本轮初次项目选集165/167：运行器临时目录过深，两个 managed case 的 Unix socket 地址超长，在启动前被拒绝。只修正独立临时目录后，同一源码、二进制、注册、断言与预算重新执行167项全部通过。中间失败和被中断的首次 Debug 构建记录均保留，未算作成功。

上述输入、产物、原始失败与验证范围见[本轮修复审校](evidence/v0.3.0/2026-11-13-ci-resumption/review.json)；Admin HTTP早期组件详情见[组件证据](evidence/v0.3.0/2026-11-13-admin-http-incremental/review.json)。

## Fuzz：仍有开放阻塞，私有提案未合入

旧候选23的[完整 CI 43417908994](https://github.com/ErosZy/capsid/actions/runs/43417908994)已结束且失败；其 WebSocket frames fuzz 在原60秒门槛超时，其余结果不能替代本轮新源码接受。

本轮按实际 CPU profile 在私有副本测试块式 XOR 与批量复制：保留完整原 oracle和fatal fuzzer/ASan/UBSan，独立掩码模型287280项通过；165份相同输入、每份程序19800次调用的 ABBA 对照中，CPU中位数比约0.4305。但提案的原失败种子及固定种子1/42全部超过原512 MiB RSS门槛。仅调整 fixture 分配的组合也在三种子失败，故两者均未合入。没有放宽60秒、512 MiB、每输入2秒、64 KiB或10000次预算，没有调小 sanitizer quarantine，也没有把同种子说成相同变异序列。

这些是被拒绝的局部优化，不是正式产品性能点或 fuzz 修复。详见[原始范围及拒绝结论](evidence/v0.3.0/2026-11-13-ci-resumption/rejected-fuzz-prototypes.json)。

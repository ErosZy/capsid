# Host Embedding and Integration Specification

This document is for gateways, servers, worker pools, and other embedders that link
`libcapsid_runtime.a` directly. It combines the embedding interface (C ABI) with the
integration specification (threading/event loop/backpressure/ABI upgrades).

- The public interface is authoritative in [`include/capsid/runtime.h`](../include/capsid/runtime.h);
  the full symbols and field comments are defined by the public header.
- The current `CAPSID_ABI_VERSION == 7`; every config structure must be initialized
  with the corresponding `*_init()` first. Do not zero-fill by hand or guess the
  structure size.
- Capsid Runtime only provides isolated workers and the C ABI; it does not implement
  HTTP listening, scheduling, retries, or application rollout for the host.

## Lifecycle

A typical host flow is:

1. After `capsid_worker_config_init()`, fill in `worker_path`, resource, and security policy;
2. `capsid_worker_spawn()` creates a worker (it synchronously validates and deep-copies
   all nested config strings, rules, and policies; after it returns, the host may free
   the original config memory; changing policy requires creating a new worker);
3. `capsid_worker_load_bundle()` or `capsid_worker_load_bundle_named()` loads a source bundle;
4. On the current POSIX ABI, connect `capsid_worker_fd()` into the host event loop;
5. Write request headers/body/end and replenish bidirectional credit as events arrive;
6. Keep calling `capsid_worker_next_event()` to consume response, log, audit, and exit events;
7. After `capsid_worker_shutdown()`, continue draining, and finally call `capsid_worker_destroy()`.

After creation, the bundle must be sent first, then the host waits for
`CAPSID_EVENT_READY`; no requests may be sent before READY.

### Trusted bytecode

`capsid_worker_load_trusted_bytecode_named()` can skip source parsing and load module
bytecode generated by an identical Capsid/QuickJS build. It is an optional optimization
for host build pipelines, not an application upload format.

QuickJS bytecode is not guaranteed compatible across versions, compiler options, or
architectures, and the deserializer is not a security boundary. Corrupted, mismatched,
or attacker-controlled bytes can cause memory corruption; therefore only host-generated
artifacts with verified digests may be loaded, never tenant input. `source_name` must
also exactly match the module name embedded at compile time. Regular applications
continue to use the source bundle API.

## Threads and event loop

A `capsid_worker` may be driven by only one host thread at a time. Creating, writing
requests, reading events, cancelling, and destroying must all be serialized; if the
gateway has multiple I/O threads, pin each worker to an owner loop and deliver commands
to it through a thread-safe queue.

On the current POSIX ABI, `capsid_worker_fd()` returns a non-blocking Unix socket. The
host should:

1. listen for writable when there is data to send, and listen for readable at all times;
2. when writable, keep calling `capsid_worker_flush()` until `CAPSID_OK` or
   `CAPSID_WOULD_BLOCK`;
3. when readable, keep calling `capsid_worker_next_event()` until
   `CAPSID_WOULD_BLOCK`;
4. after receiving `CAPSID_CLOSED`, `CAPSID_PROTOCOL_ERROR`, or `CAPSID_EVENT_EXIT`,
   stop reusing that worker and replace it according to the application rollout policy.

Most I/O APIs may return `CAPSID_WOULD_BLOCK`; that is a normal backpressure signal,
not a worker fault or a reason to busy-loop retry. An operation that returns
`WOULD_BLOCK` does not commit half a logical frame.

Do not block on a shared reactor waiting for a single worker. Startup, requests, and
shutdown should all have host deadlines; the worker's built-in deadline is a second
boundary and does not replace the gateway deadline.

`capsid_worker_fd()` is the ABI v7 integration surface and should not be
interpreted as a permanent cross-platform abstraction. On POSIX it returns a
non-blocking Unix socket fd; on Windows it returns a CRT fd backed by a loopback
TCP socket. Cross-platform hosts should therefore keep the platform-specific
worker-event-source adapter isolated and must not make the business layer depend
on Unix fd semantics. Windows embedding is validated natively through the
first-party Host tests on the `windows-latest` runner, but the documented POSIX
contracts still define the reference semantics. Platform support tiers are
described in [Architecture and Product Boundary](architecture.md#platform-contract).

## Requests, credit, and backpressure

A request ID must be non-zero and unique within a worker until response end, error,
timeout, or cancel completes. The request order is:

```text
begin_request
  → after REQUEST_CREDIT, write_request (may repeat)
  → end_request
  → RESPONSE_HEAD / RESPONSE_BODY / RESPONSE_END
```

1. Call `capsid_worker_begin_request()`;
2. Call `capsid_worker_write_request()` only within the credit granted by
   `CAPSID_EVENT_REQUEST_CREDIT`;
3. Call `capsid_worker_end_request()`.

Response body is also credit-controlled. After the host consumes or successfully
forwards a chunk of `CAPSID_EVENT_RESPONSE_BODY`, it returns the corresponding bytes
with `capsid_worker_grant_response_credit()`. Do not grant credit in advance based on
expected consumption; otherwise a slow downstream client shifts memory pressure onto
the host. Credit is isolated per request ID; a global queue budget cannot replace
per-request backpressure.

Events for each request ID arrive in the order response head → zero or more body →
response end, or error/timeout. Different request IDs may interleave, so the host must
keep independent state per ID.

Cancellation uses `capsid_worker_cancel()`; repeated cancellation is idempotent.
Cancellation propagates to the handler, upload body, response backpressure, and egress
fetch. Legitimate frames already in flight from an old request may still need draining,
so the host should not immediately reuse the request ID.

## Event and memory lifetime

`capsid_event.payload` and the views obtained from the following functions point to
runtime-owned event buffers:

- `capsid_response_header_at()`;
- `capsid_response_status_text()`;
- `capsid_audit_record_decode()`.

These views are guaranteed valid only until the next `capsid_worker_next_event()` call
on the same worker. They must be copied before crossing callbacks, threads, async
writes, or queueing; do not store raw pointers. Response headers should be decoded with
the count/iterator API to preserve the distinct values and order of multiple
`Set-Cookie` headers. Memory metrics decode copies numeric values and does not retain
the payload view.

Inputs that the host supplies to `begin_request`, bundle, and policy are also managed at
the call boundary except where the documentation explicitly says they are copied
synchronously; the safest rule is to keep them valid until the call returns.

The host must keep draining `CAPSID_EVENT_LOG` and `CAPSID_EVENT_AUDIT`. They are
bounded channels and cannot replace an unbounded log queue. A worker should be destroyed
and replaced after `CAPSID_EVENT_EXIT`, a protocol error, or a synchronous CPU timeout.

## SSE, streaming, and no-buffer

Capsid does not treat SSE as a special protocol: it is a long-lived response body
stream. The host should forward headers immediately after receiving the response head
and write each body frame downstream; do not wait for response end to aggregate. For
`text/event-stream`, responses without `Content-Length`, or explicitly streaming routes:

- Disable proxy-layer automatic response buffering and whole-response compression buffering;
- Return worker credit only after the downstream write completes;
- Cancel immediately on client disconnect;
- Set host limits for total connections, per-connection idle time, and unacknowledged bytes;
- If the gateway protocol requires flushing, flush on event boundaries or a
  product-defined throttling policy; do not rely on empty frames.

Capsid does not generate proxy-specific headers such as `X-Accel-Buffering`. Whether to
set, delete, or interpret those headers is host/deployment policy.

## Errors, cancellation, and shutdown

`CAPSID_EVENT_ERROR` is either a request-level error (request ID non-zero) or a
worker-level error (ID zero); `CAPSID_EVENT_REQUEST_TIMEOUT` indicates a worker soft
deadline; `CAPSID_EVENT_EXIT` indicates child process termination. The host must
distinguish all three from application HTTP 5xx responses and must not disguise
protocol/isolation failures as application responses.

Call `capsid_worker_cancel()` on downstream cancellation, host deadline, or request body
read failure. After cancel, discard late events for that ID but keep driving the socket
until the runtime finishes internal cleanup. Do not reuse a cancelled ID.

Graceful shutdown starts by removing the worker from scheduling, waits for inflight to
reach zero, then calls `capsid_worker_shutdown()` and continues flush/read. If the
worker has not exited by the host shutdown deadline, call `capsid_worker_terminate()`,
and always finish with `capsid_worker_destroy()`. destroy is abortive cleanup and must
not happen in an async callback that still holds a payload view.

## Timeouts and destruction

`request_timeout_ms` produces `CAPSID_EVENT_REQUEST_TIMEOUT`:

- An async hang only cancels the corresponding request; the worker can continue to be used;
- After the QuickJS interrupt breaks a synchronous CPU dead loop, the worker is
  considered disposable.

`capsid_worker_destroy()` is a bounded reclamation path that escalates from graceful
shutdown to SIGTERM and SIGKILL. The host should not rely on the application bundle
exiting on its own.

## Network and security configuration

`egress_policy == NULL` means all egress Fetch is denied by default. If
`capsid_capability_policy.net_policy` is also configured, the two are intersected. The
hostname, the actual address after DNS resolution, and every redirect are re-checked.

`strict_sandbox`, `sandbox_required_features`, `resource_limits`,
`sandbox_cgroup_path`, and `sandbox_network_namespace_fd` are host interfaces and are
not exposed to JavaScript. See:

- [Host Capability Policy](capability-policy.md)
- [Linux Strict Sandbox](linux-sandbox.md)

## Sandbox and resource responsibilities

JavaScript cannot enlarge permissions. The host is responsible for constructing
capability, egress, cgroup, namespace, and file path policies, and for verifying the
actually installed sandbox features in the READY flags. Production Linux should use a
strict sandbox and controlled cgroup; benchmark data without strict mode must not be
presented as production isolation evidence.

`capsid_worker_request_memory_metrics()` is a diagnostic interface that walks the
QuickJS heap. It is not part of regular telemetry sampling, is not on the request hot
path, and is not exposed to JavaScript. Process RSS/PSS should be read from the worker
PID rather than measuring only the gateway or repeatedly spreading the whole gateway
across every worker.

## ABI version policy

The current ABI is v7. The compatibility rules are:

- The same ABI version does not change existing struct fields, sizes, alignment, enum
  values, or function signatures;
- Independent functions and new event enum values may be added, but old hosts must
  treat unknown events as explicit errors and must not silently interpret them;
- Extending an existing struct requires an ABI version bump unless that struct defined
  both-sides-verified size negotiation from the start;
- Existing exported symbols are not removed or renamed within the same ABI version;
- The library initializer may only write within the range allowed by the caller's
  `struct_size`;
- The library must pass the `abi_v7_current_header_current_library` test compiled and
  linked against the frozen v7 header.

When upgrading a host, first deploy a gateway that recognizes the new events, then
enable the feature that produces them. Diagnostic-class new events appear only when the
host explicitly requests them, so they do not affect v7 hosts that have not called the
new functions.

## Launch checklist

- Pin hashes for the worker, library, bundle, capability manifest, and build metadata;
- Verify READY, sandbox flags, application health requests, and maximum body/headers;
- Verify request/response credit, slow clients, SSE, cancellation, and gateway shutdown;
- Verify worker crash, protocol errors, soft/hard timeout, and replacement policy;
- Observe the worker PID's cgroup memory/CPU/PID limits separately from gateway resources;
- Keep release evidence for old header/new library, full Release tests, and delegated sandbox.

## Minimal configuration example

```c
capsid_worker_config config;
capsid_worker_config_init(&config);
config.worker_path = "/path/to/capsid-worker";
config.request_timeout_ms = 1000;

capsid_worker *worker = NULL;
capsid_result result = capsid_worker_spawn(&config, &worker);
if (result != CAPSID_OK) {
    /* Log capsid_result_string(result); this startup failed. */
}
```

Production integration must also handle `WOULD_BLOCK`, all event types, stream credit,
cancellation, worker replacement, and host process shutdown. The full symbols and field
comments are defined by the public header.

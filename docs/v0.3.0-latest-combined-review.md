## 2 P1：写入失败后的新 pool 自持有与实际 Worker 累积

相关代码：
[main.cc 的 pool_box](../src/host/main.cc#L762)、
[abort_activation](../src/host/main.cc#L876)、
[finish_activation 失败分支](../src/host/managed_host.cc#L946)。

`pool_box` 是 `shared_ptr<shared_ptr<GenerationPool>>`，被 pool 自己保存的
`on_drain_complete` 捕获。`*pool_box = pool` 后形成引用环：

```text
GenerationPool -> options.on_drain_complete -> pool_box -> GenerationPool
```

正常 drain 会在回调中 `reset()` 断开环。但 persist 失败时，`abort_activation`
只恢复旧路由视图，没有请求新 pool drain；计划释放也不能触发新 pool 析构，
因而回调始终没有执行。`GenerationPool::create_adopted` 已明确要求不自持有，
当前接线绕过了原本依靠计划释放进行回收的约定。

在仅属于本次探针的临时应用中，用 `active.json` 目录阻止原子写入，确认新
Worker 已 READY、部署状态 failed、旧 v1 HTTP 仍返回 200。容量配置为
`workersTotal=1`、`activationSurgeWorkers=1`。两轮独立探针均得到：

| 失败次数 | 实际 Worker 数 | Host 线程 |
| --- | ---: | ---: |
| 0 | 1 | 8 |
| 1 | 2 | 10 |
| 2 | 3 | 12 |
| 3 | 4 | 14 |

第二轮 Host RSS 从 11,736 增至 17,124 KiB。Host 最终正常退出，探针 Worker
随后全部退出；问题发生在 Host 继续运行的失败部署路径。

现有 `host_managed_deploy_persist_failure_aborts` 本轮通过，但其
`TransactionHarness` 没有生产 `pool_box` 回调接线，因此不能检出此回归。

同一回滚路径还存在源码可确认的引用残留：prepare 每次把旧 pool 加入
`draining_pools`，abort 未撤销这次插入；drain 回调又只删除第一个匹配项。
连续失败可保留旧 pool 的重复引用，应一并处理，不能仅让新 Worker 退出。

整改及验收：

1. 区分未提交、已激活及正在 drain 的 pool 所有权，取消新 pool 对自身的长期
   强引用，或设计有明确中断和回滚出口的生命周期持有。
2. persist/prepare 失败后在可 join 的控制线程上排空、释放未发布 pool；撤销
   本次旧 pool 停车引用。避免持 `pools_mutex` 执行会等待回调的 join。
3. 同步核对 `abort_reserve` 与 `release_drained`：未提交 pool 的 drain 通知
   不能再次释放已经回滚的容量，也不能扣减同应用其他 generation 的余额。
4. 增补真实 Host 的 `websocket_managed_deploy-persist-failure`，重复至少三次
   失败并断言旧版本可用、新 Worker 消失、线程回到基线、容量可复用。
5. 加对象级断言：pool/factory 引用释放、线程完成 join、无重复停车引用。
   保留独立 coordinator 单测，同时覆盖生产接线，避免测试回调与实现脱节。

上述新名称为建议，当前尚未注册。

**2026-10-14 GLM 修正结果（本节 P1，写入失败回归）：**
`pool_box` 改为 `std::weak_ptr`（恢复 create_adopted 的不自持约定）；abort 路径
通过纯引用计数析构未发布 pool（~GenerationPool = request_drain + wait，在协调
线程上排空并 join），drain 钩子先 lock——正在析构的 pool 既不会自我复活，也不
会重复释放容量（abort_reserve 已结算）。`abort_activation` 与 `abort_retire`
均撤销旧 pool 的停车引用（删除全部匹配项），drain 钩子同样删全部匹配。新增
`websocket_managed_deploy-persist-failure`（真实 Host，连续 3 次失败，断言
旧版本可用、新 Worker 消失 ≤12s 有界 teardown、线程回基线、容量可复用）：

`persist-failure/dpf-red.log`）；修复版 6/6 通过且 reapMs ≤2ms（析构先于 failed
可见完成）。稳定性：churn 场景的请求期限放宽到 5s（1s 期限在加载机上把调度

## 3 P1：新增换代回归未形成稳定、完整的验收

本轮独立选取 17 项，实际 **16/17，零 skip**。唯一失败为
`websocket_managed_replacement-recursion`：第 10 个部署操作状态 failed，未到
最终 RSS/VmSize 断言。随后三次单独复跑全部通过，应保留一次失败与三次通过
的记录，不能用最后一次通过覆盖原失败。

用例每轮只等待 Worker 数回到 1。这个条件不等同于旧 pool 的 drain 回调完成
及 ledger surge 余额已归还；源码存在通知和清理的时间窗口。失败日志在 validate
之后没有进入 worker_starting，符合 admission 阶段失败的表现，但当前 Admin
响应不包含失败原因，本轮未将“capacity exceeded”定为已证实的具体原因。

需要提供可观察的 generation 回收完成条件，或在可共享的生产组件中验证
drain/ledger/引用完成，再开始下一轮。保留故障原因及各阶段状态用于判断；
不靠放宽内存阈值或任意 sleep 结束验收。并补“最后一次 retire 后不再执行
其他 Admin 操作”的对象归还检查。

GLM 的 13 项和 64 项报告均未包含新增用例；`index-p1fix.json` 仅记载该项
Passed 和禁用回收后的 Red 描述，没有归档对应独立 JUnit、观测 JSON 或 Red
原始输出。应把新增用例纳入必需测试清单，补精确命令、结束状态、输入/源码/
二进制摘要与完整报告。已补存的旧 JUnit 副本不能代替新用例的证据。

## 4 workerd 强兼容差异：17 项仍未解决

当前 Host、Worker 与相同 worker 输入重新对照锁定 workerd：27 个 API 观察点
中 14 个差异，另有 3 个事件差异。完整输入及结果见
[测试完整性审校第 3 节](v0.3.0-test-completeness-review.md#3-已确认需要固定为回归的-17-个观察点)。

| 组 | ID | 本轮仍存在的差异 |
| --- | --- | --- |
| 参数转换 | C01–C04、C07、C10–C12 | send 缺参/Symbol、close 小数/reason Symbol、binaryType 对象、URL 与 protocols 的转换和异常类别 |
| 对象构造 | C05/C06、C13/C14 | CloseEvent 小数/null，Response 101 无 endpoint 与尚未 accept 的构造阶段 |
| listener | C08/C09 | 非法 callback，once options 修改后的移除与重注册 |
| 异步消息 | C15 | reference 允许后续 message handler 在前一 await 未完成时开始；Capsid 串行等待 |

不能把 reference 对非法 wire 的宽容直接扩展为所有行为的目标；普通 API、
对象、事件与正常生命周期按强兼容目标修正，额度与部署策略独立声明。

前轮 A–D 任务全部保持待完成：正式 API/Response/事件回归、修实现、严格
两端报告比较器，以及必需 reference 门禁。两项现有 reference 本轮均通过，
说明现有断言通过，不表示上述观察点已经兼容。

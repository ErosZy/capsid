## 1 P1：失败部署回收仍会留下额外存活 Worker

正式 `websocket_managed_deploy-persist-failure` 在 70 项集合中失败：第三次
回滚后存活 Worker 为 `[479129, 479156]`，断言位于
[生命周期测试](../tests/test_websocket_managed_lifecycle.mjs) 的回收等待处。
该枚举已经排除 zombie，并校验 exe 是本次 fixture 的 Worker，不能把这条
观察解释为仅有已退出子进程尚未 wait。

| 执行 | 结果 |
| --- | --- |
| 独立必需集合 | 69/70，零 skip；仅此项失败 |
| 不改代码，单独复跑 1 | 通过，三次回滚均回到 1 Worker、8 线程 |
| 单独复跑 2 | 失败，第三次回滚仍有 `[480115, 480136]` |
| 单独复跑 3 | 通过，三次回滚均回到 1 Worker、8 线程 |
| 加只读采样的诊断副本 | 第一次回滚即复现；约 1,020 ms 时为 2 Worker、Host 10 线程，之后回收等待失败 |
| 同一诊断副本后续六次 | 均通过；保留全部记录，不覆盖失败 |

生产回归的等待上限已是 20 秒，第二次单独失败总耗时约 20.30 秒。通过时
reapMs 为 1 ms；这轮不能靠继续放宽窗口验收。GLM 原 15/66 绿灯是真实的
历史结果，但不足以关闭间歇问题。

原强自持环的消除仍成立，不能直接把这次失败归因于同一个环。优先排查
[generation_pool.cc](../src/host/generation_pool.cc) 的 notifier：`weak.lock()`
会临时取得强引用，最后一个引用若由 executor 通知线程释放，析构线程与
`wait()`/join 的关系需要直接验证。这只是源码排查方向，当前没有取得可归因
的原生调用栈，不将其写作已证实根因。

需补确定性交错的回归：暂停 notifier 持有临时引用，触发 prepare 后 persist
失败及引用释放，再继续 notifier；断言 pool/factory 最终释放、executor 与
pump 完成 join、子进程归还、容量可复用。同时保留真实 Host 多次回滚用例，
不能用独立事务 harness 替代生产回调接线。

## 2 P1：跨请求预建 endpoint 仍与 reference 不同，正式回归测偏

[api-compat.mjs](../tests/fixtures/workerd-ws/api-compat.mjs) 的 `/retransfer`
每次执行都把 `globalThis.__retransfer` 替换为新建 Response。因此第二次实际
取出的是前一请求预建、尚未移交的另一个 endpoint，并不是同一 Response
第二次移交。[runner](../tests/test_workerd_ws_fixtures.mjs) 又用普通 `fetch()`
发第二次请求，没有 Upgrade，所得 500 无法证明重复移交 guard 有效。

本轮直接加载这份正式 fixture，不修改 worker 代码，连续发两次真实 Upgrade：

| 操作 | 锁定 workerd | Capsid single-worker / static-pool / managed |
| --- | --- | --- |
| 第一次 `/retransfer` | 101、echo、close 1000 | 全部相符 |
| 第二次 `/retransfer`，使用前一请求预建 endpoint | 500，跨请求 I/O 错误 | 全部 101、echo、close 1000 |

这是新的请求归属差异。与它分开的“同一已移交 Response 再移交”在独立旧探针
中已经修好，三模式均明确 500；不能把两者混为同一项或回退该修复。

需把正式用例拆为三类，第二次均发送真实 Upgrade，并校验失败后的资源终态：

1. 同一 Response/endpoint 重复移交：第一次成功，第二次明确失败。
2. 前一请求创建但未移交的 pair/Response：固定 reference 的跨请求限制，
   检查 endpoint 创建归属与 transfer 请求归属。
3. 当前请求创建的新 pair：连续两次独立升级均成功，作为正常控制。

跨请求预建 pair 不应只依靠 `transferred` 标志判断。实现方案需保留已经接入
连接的事件 owner 和延迟 accept 的有效路径，避免用禁止所有异步 callback
的方式处理这个边界。

## 3 P2：扩大转换表后仍有 9 个不符观察点

在前轮 38 个 API 观察点上新增 14 个相邻控制，共 52 点；三种 Host 模式都
复现下表 9 个差异，其余 43 点一致。这里只按结果/异常类型比较，不要求错误
文本完全一致。两端使用同一 worker 源码及锁定 reference/client。

| 输入或观察 | workerd | Capsid |
| --- | --- | --- |
| `close(1000, 123n)` | 接受 | TypeError |
| `new CloseEvent('x', {reason:123n}).reason` | `"123"` | TypeError |
| `new CloseEvent('x', {reason:null}).reason` | `"null"` | 空字符串 |
| `close(Object(1000n))` | TypeError | 接受 |
| `new CloseEvent('x', {code:Object(1000n)}).code` | TypeError | 1000 |
| CloseEvent code 为 NaN | 0 | NaN |
| CloseEvent code 为 Infinity | 0 | Infinity |
| CloseEvent reason 为孤立 `\ud800` | U+FFFD | 保留 U+D800 |
| code/reason/wasClean getter 读取次序 | code、reason、wasClean | code、reason、code、reason、wasClean |

`close()` 和 CloseEvent 对 reason 的 BigInt 检查属于本次新增误拒绝：reason
走字符串转换，不能与 code 的数值转换共用原始类型 guard。反过来，裸 BigInt
guard 又漏掉了装箱 BigInt，`Number()` 接受它而 reference 拒绝。

[websocket.js](../js/websocket.js) 的 `toUSVString()` 当前只拒绝 Symbol 后
调用 `String()`，未替换孤立代理项；CloseEvent 的 `?? ''` 还合并了 null 与
undefined，且提前检查 getter 后再次读取。应分别实现 code 与 reason 转换，
按 reference 处理有限值、原始值转换、默认值和单次读取，保存局部结果后构造
事件。补齐这 14 个控制，保留前轮大数/负数/分数和普通输入，防止修一组退一组。

## 4 P2：正式 C12 握手全部失败，测试仍通过

正式 runner 的协议矩阵只断言构造及请求 header，没有断言 open、选中
protocol 或关闭结果。本轮在不改变断言、worker 或 peer 行为的诊断副本中
记录原始请求、解析 key 和 `/state`，分别运行 reference 和 single-worker：

- 8 个合法输入的 `Sec-WebSocket-Key` 均未解析到；正则带行尾锚点却没有
  多行标志，而请求的 key header 并不位于整个 head 的末尾。
- peer 用错误 key 算出 Accept，8 个结果均只有 `state:3`、code 1006、空
  `protocolAtClose`；iterable 仍正常抛 SyntaxError。
- 两端 diagnostic runner 都 exit 0。所谓“这个 harness 下 getter 不对”
  实际对应失败握手，不能据此删除成功协商的黄金。

本轮正确的独立 peer 已验证三模式的 header、open 时 protocol 和 close 1000
都与 reference 相符，所以这是正式测试的覆盖问题，不能写成实现仍不支持
C12。修 peer 的 key 解析与帧处理后，每个合法输入必须断言实际 open、选中
protocol、close 1000/clean，并对错误 Accept 增加预期失败控制。第二节的
普通 HTTP 500 和此处的 1006 都说明断言数量不能代替对目标路径的验证。

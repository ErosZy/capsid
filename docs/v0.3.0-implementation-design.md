# Capsid v0.3.0 技术方案

本方案用于完成 FetchRPC v4 和 WebSocket 里程碑，并修复审校发现的 ABI、进程回收、缓冲和性能证据问题。实施顺序见 [GLM 执行计划](superpowers/plans/2026-10-12-v0.3.0-remediation-and-delivery.md)。范围以 [ROADMAP](../ROADMAP.md#v030-fetchrpc-v4-and-websocket-foundation) 为准。

下文的新增接口、A2 协议布局、资源默认值是本次实施的设计输入。GLM 必须先完成对应契约测试，将最终字节布局和错误表写入 [FetchRPC 契约](fetchrpc-v4.md)，再实现通道运行时。它们尚未成为已实现能力。已有 v3 线格式、发布过的 ABI v7 布局和沙箱保证继续受回归测试约束。

## 1 设计决策

| 项目 | 实施方案 |
| --- | --- |
| ABI | 保留 v7 原结构，增加独立 protocol options 和 spawn 入口；新描述符从第一版开始实行双向大小协商 |
| 协议修正 | 在 v4 中登记 A2 修正案，用显式能力位区分修正后的通道布局；v3 和 v4 carriage 的基础载荷继续兼容 |
| 通道寻址 | 每条 worker IPC 连接独立分配 host 权威的 u32 channel ID；通道帧显式携带 ID |
| 出站关联 | worker 分配 u64 dial ID，host 返回分配的 channel ID；同时携带 URL 和 subprotocol 列表 |
| 所有权 | 101 提交时，把资源从握手请求移交给连接 owner；HTTP response 清理不释放活跃连接 |
| 网络 | host 处理 HTTP Upgrade、RFC 6455、DNS 和 TLS；worker 仅处理 JS 消息及 FetchRPC 通道 |
| 流控 | 双向字节 credit；传输队列、消息重组和 JS 待发队列分别计费，并受 worker 和 host 总预算约束 |
| JS 行为 | 由锁定 workerd 源码和实际 fixture 确定；Capsid 的资源限制记入 conformance deviation |
| 测量 | 修复车道和收集器后重新生成点；每个数字保留来源、姿态、原始样本和可校验的摘要 |

此版本不实现 hibernation、压缩扩展、Binding RPC v2、`ctx.waitUntil()`、Wrangler 工作流或 QuickJS 惰性编译。普通 WebSocket `accept({ allowHalfOpen })` 是否支持以及默认行为，由锁定参考测试确定，不能把它归为 hibernation 后直接排除。

## 2 ABI v7 和配置入口

### 2.1 恢复发布过的结构

从 tag `v0.2.2` 对应的 `aef6020` 恢复 `capsid_worker_config` 的字段、顺序、大小和对齐，移除后来加入的 `protocol_version`、`protocol_reserved`、`protocol_capabilities` 尾部。恢复 `tests/compat/runtime_v7.h` 原快照；它不能跟随新实现扩展。

旧的 `capsid_worker_config_init()` 仍按原 v7 大小初始化。旧调用方往往传入未初始化的结构，因此不能改成读取其中尚未定义的 `struct_size`，以此冒充兼容修复。旧的 `capsid_worker_spawn()` 固定采用 v3。

现有 `capsid_event`、公开枚举的既有数值和函数签名也保持不变。v4 通道事件通过新增枚举值和 typed decoder 表达；新行为只由显式选择 v4 的入口触发。

### 2.2 独立描述符

新增接口采用下列形状，最终名称和错误映射在 ABI 任务中同步冻结：

```c
capsid_result capsid_protocol_options_init(
    capsid_protocol_options *options, uint32_t caller_size);

capsid_result capsid_worker_spawn_ex(
    const capsid_worker_config *config,
    const capsid_protocol_options *options,
    capsid_worker **out_worker);

capsid_result capsid_worker_get_protocol_info(
    const capsid_worker *worker,
    capsid_protocol_info *out_info, uint32_t caller_size);
```

`capsid_protocol_options` 包含 `struct_size`、descriptor version、wire version、reserved、requested capabilities，以及可选的 channel limits 描述符。`options == NULL` 等价于旧 v3 入口。descriptor version 与 `CAPSID_ABI_VERSION` 分开，第一版为 1。

所有新描述符都遵守以下规则：

- 初始化函数获得显式 buffer 大小；不足以容纳固定前缀时返回参数错误，不写越界。
- 初始化只写 `min(caller_size, library_known_size)`；输入解析逐字段检查是否在 `struct_size` 内。
- 解析允许未来调用方提供较大结构，只读取已知版本的字段；未知 descriptor version 明确拒绝。
- nullable 指针的内容在 spawn 时同步复制为不可变快照，后续拨号不借用调用方临时内存。
- unknown capabilities、依赖不满足、reserved 非零和非法 limits 在创建 socketpair、子进程、cgroup 或 Windows handle 之前拒绝。
- READY 前查询 protocol info 返回 `CAPSID_WOULD_BLOCK`；READY 后返回 wire version、双方能力和有效交集。

host 内部和 C++11 wrapper 使用新入口。C11 header、C++11 wrapper、原始 v7 consumer、较小新描述符和较大未来描述符都需要独立链接和哨兵测试。

### 2.3 启动资源回收

通过 RAII 或等价的单一 owner 管理未发布的进程、IPC FD、Windows process/thread handles 和临时 cgroup 状态。只有成功返回 worker 时才转移所有权。任意返回失败或异常都关闭 FD、终止并回收真正的 child；不能把尚未记录 PID 的半成品交给 `capsid_worker_destroy()`。

## 3 FetchRPC v4 A2 修正案

### 3.1 版本与能力

帧头保持 24 字节。magic 是数值 `0x43545257`，LE 字节为 `57 52 54 43`；不要用错误的 ASCII 注释替代黄金字节。类型 1 到 18 的 v3 定义保留，既有通道类型 19 到 26 也不重新分配。

登记 `CAP_CHANNEL_LAYOUT_A2 = 1u << 3`。Duplex、Upgrade、HalfClose 均要求 A2；Upgrade 和 HalfClose 还要求 Duplex。只有 A2 而没有 Duplex 的组合拒绝。未知位和 reserved 非零仍为致命协议错误。

双方不宣告通道能力时，v4 carriage 使用现有 Hello/READY 形状。启用 A2 的一方使用明确修正后的载荷；旧 v4 parser 会拒绝未知位，不能误读新布局。有效功能取双方能力交集，并验证依赖闭包。禁用功能的帧在状态解码层拒绝，不能只检查帧号合法。

worker bootstrap 只允许第一帧为 HELLO，wire version 为 3 或 4；成功验证整帧后锁定版本。后续任何跨版本帧都拒绝，连接内不降级。首帧不是 HELLO、重复 HELLO、坏 READY 和假能力交集都有确定错误表。

### 3.2 Hello 和 READY

v4 carriage 为完整合法的 v3 startup payload 加 8 字节能力尾。A2 则在 startup payload 与能力尾之间增加长度标记的 limits extension：

```text
v3 startup payload
u32 extension_size = 48             仅宣告 A2 时存在
u16 extension_version = 1
u16 reserved = 0
u32 max_channels
u64 max_message_bytes
u64 reassembly_budget_bytes
u64 send_budget_bytes
u32 close_timeout_ms
u32 dial_timeout_ms
u32 idle_timeout_ms
u32 per_channel_queue_bytes
u32 capabilities
u32 reserved = 0
```

字段均为 LE。extension version/size、算术溢出、全部预算关系和 trailing bytes 必须验证。原始 v3 decoder 的 cursor 到达 startup 结束后才解析扩展；不能从全零占位数组生成声称合法的 HELLO。

READY 的 wire payload 继续在 compatibility ID 和 sandbox proof 后追加能力尾。client 先验证能力尾并保存 typed protocol info，再把去掉能力尾的 READY payload 交给原来的 sandbox proof 验证路径。binding proof 的 digest、seccomp、Landlock 和 namespace 检查不因 v4 而变弱。C ABI 的 READY 载荷说明同步更新，wire 协商由 raw peer 测试验证。

### 3.3 通道载荷

所有通道帧头中的 `request_id` 保留为 0；channel ID 必须从 payload 获取。owner request ID 和 dial ID 各有独立字段。ID 在当前 IPC 连接内从 1 递增，不复用；耗尽时拒绝新通道并由 supervisor 有序更换 worker。

以下是 A2 的实现布局输入。契约任务必须将枚举数值、长度上限、方向和错误字符串补全为规范表，更新 vectors schema，并生成独立解码测试：

| 帧 | 载荷 |
| --- | --- |
| OPEN 19 | `u32 channel_id, u64 dial_id, u8 owner_kind, u8 channel_kind, u16 reserved, u64 owner_request_id, u64 max_message_bytes, u32 url_size, url bytes, u16 protocol_count, length-prefixed protocols` |
| ACCEPT 20 | `u64 dial_id, u32 channel_id, u64 accepted_max_message_bytes, length-prefixed selected_protocol` |
| REJECT 21 | `u64 dial_id, u32 channel_id, u32 reason_code, length-prefixed bounded diagnostic` |
| DATA 22 | `u32 channel_id, message fragment bytes`；flags 为 start/end/text |
| CREDIT 23 | `u32 channel_id, u64 credit` |
| HALF_CLOSE 24 | `u32 channel_id` |
| CLOSE 25 | `u32 channel_id, u8 close_kind, u8 flags, u16 code, u16 reason_size, reason bytes` |
| CANCEL 26 | `u32 channel_id, u32 terminal_reason`；CONFIRM 下未分配 dial 使用 `channel_id=0` 并追加 `u64 dial_id`；host 拒绝仍用 REJECT |

worker 出站 OPEN 为 `channel_id=0`、非零 dial ID、`ws:`/`wss:` URL 和候选 protocols。host 分配 ID 后 ACCEPT；失败使用 REJECT。入站通过 Upgrade head 预留；不使用 host 主动 OPEN。protocol 字符串使用 u16 byte length，URL 用 u32 byte length，diagnostic 用 u16 byte length；整个 payload 仍不得超过 64 KiB。

2026-10-13 补充：channel ID 按 wire 宣告次序单调分配，dial ID 独立为单调 u64，均不复用。T05 的 v4.2 修订使用能力 bit 4 `CAP_CHANNEL_CONFIRM` 和 ACK 27（`u32 channel_id, u64 dial_id, u32 kind`），增加 ACCEPT/REJECT 的 result barrier 与取消/transport Close 的 terminal barrier。ACCEPT 未确认前不能产生 DATA；取消后排队结果/数据只验证和排空，不投递 JS。确认或期限到达后回收有界关联；期限到达关闭整条 IPC，避免丢掉关联后误判迟到 ACK。双端 FIFO 回放和真实 IPC raw-peer 覆盖交错与满队列重试。本次入站续接已接通 JS/network/owner，worker 在协商 CONFIRM 时宣告 27（DUPLEX/UPGRADE/A2/CONFIRM），不宣告 HALF_CLOSE。普通 Close 的接收修正为 v4.2.1，字节布局不变。完整规则见 [wire contract §3.5.1](fetchrpc-v4.md#351-confirmation-amendment-v42-2026-10-13)。

DATA 的有效消息字节最多为 `65536 - 4 = 65532`，credit 只按有效消息字节计费。flags 的 text 属性在一条消息中不能改变。单片消息同时带 start/end，多片消息只有首片 start、末片 end。

入站 Upgrade 不再额外发送 OPEN：RequestHead 的 upgrade 尾为 `u32 channel_id, u64 max_message_bytes`；ResponseHead 的 101 upgrade 尾返回同一 ID 和接受的消息上限。成功 ResponseHead 是 pending 到 open 的提交点。非 101 响应释放 pending reservation，不能留下通道或产生 DATA。

101 upgrade 与 fixed-body flag 互斥。selected subprotocol 从 worker 响应头提取，host 必须确认它属于请求列表且只能选择一个。Connection、Upgrade、Sec-WebSocket-Accept 由 host 生成。升级响应不发送普通 ResponseEnd；typed upgrade event 明确结束 HTTP 请求记账并建立连接记账。

### 3.4 错误、关闭与竞态

CLOSE 的 close kind 区分发起 Close、观察到 peer Close、transport terminated。最终 close kind 数值和 flag 矩阵在契约任务冻结。code-present flag 允许表达空 Close body；1005/1006/1015 不能作为正常待发送状态码。1006 仅可用于异常终止观察，绝不能编码成网络 Close 帧。

JS CloseEvent 的触发点、`wasClean` 和收到 Close 后是否自动应答由 workerd reference fixture 决定。transport 回收另有完成通知，不把“JS 事件已派发”当成“所有写入已结束”。错误通过 REJECT、CANCEL 或原有 kError 的明确作用域表达；契约必须有 channel/request/connection 三类错误映射，禁止默默吞掉错误。

同时 Close 是合法双向动作。重复同向 Close、重复 OPEN、未知活跃 ID、数据越序、credit 溢出、无 credit 的 DATA 都有明确结果。重复 CREDIT 是再次增加额度，不称为幂等。内部清理操作可幂等，但重复 wire frame 仍由契约决定；有限 tombstone 只处理可证明来自已完成异步回调的 late completion，不宽免恶意 wire 输入。

## 4 通道状态和资源所有权

建议用项目自有 `channel_registry` 和 `channel_state` 模块承载共同逻辑，避免分别在 host 和 worker 中复制相近但不一致的状态机。

```text
reserved / dialing -> pending -> open -> closing -> closed
                          \-> rejected
open: send direction 和 receive direction 分别具有 open / half-closed 状态
```

| owner | 生命周期 |
| --- | --- |
| handshake request | 101 提交前受请求超时和断连约束 |
| duplex connection | 入站 101 提交后独立于 HTTP response；仍绑定具体 worker generation |
| request | 普通 request-bound channel 随请求终止 |
| response stream | 随 response stream 终止 |
| standalone | 出站连接独立于发起它的 HTTP response，但受 worker、generation、显式 close 和预算约束 |
| tail task | 预留值；v0.3.0 明确拒绝创建 |

资源始终记录不可变的 User/Binding authority。lifetime owner 与 permission origin 分开，移交到连接 owner 不能扩大权限。User 创建的 outbound socket 不继承 Binding 身份。

worker 为连接事件建立独立 async owner/token。101 后收到的 message/close/error 不借用已 terminal 的 HTTP request token，且不会为用户开放任意 tail task。消息回调及其 Promise 仍受 CPU、heap 和任务调度边界约束。

客户端断连、请求握手超时、dial timeout、close timeout、worker 退出和 generation replacement 都进入同一清理入口。清理顺序为：停止产生新事件，取消尚未完成的 IO，终结 pending promises，完成或中断受限写入，撤销 token/native roots，释放额度和池引用。每个通道至多派发一次 JS terminal close，所有 native owner 最终释放。

managed blue-green 切换停止旧 generation 接收新连接，对其已有 WebSocket 发 1001 并有界 drain；期限到达后强制回收。连接不能迁移到新 worker，旧 socket 回调也不能投递到替代进程上。

## 5 背压和内存预算

默认值作为首次实现的资源配置，不作为性能结论：

| 资源 | 初始设置 | 约束 |
| --- | --- | --- |
| 双向初始 credit | 各 64 KiB | 独立 u64；加法和扣减验证溢出/下溢 |
| 每条通道传输队列 | 各方向最多 4 MiB | 还受 worker/host 总预算约束 |
| 单条消息上限 | 1 MiB | 双方取较小值；硬上限 64 MiB |
| worker 消息重组总预算 | 16 MiB | 创建重组区之前预留；不随通道数无限倍增 |
| worker 待发消息总预算 | 16 MiB | JS view/native copy 均计费，外部内存也计入 |
| 每 worker 通道数 | 128 | 与 HTTP inflight 单独计数，部署方可向下限制 |
| 拨号期限 | 10 秒 | 包含解析、TCP、TLS、HTTP handshake |
| Close drain 期限 | 5 秒 | 到期中断 IO 并释放 owner |
| idle 期限 | 默认 0，禁用 | 长连接不继承 30 秒 HTTP request timeout |

提高 message 上限时必须同时满足 host、worker、JS heap 和重组预算。每次分配前预留额度，释放时归还；超限返回可复现的错误或有界关闭，不能默默丢消息。host 还按 listener/整个服务的总预算限制全部连接，不能只证明单个通道有限。

网络 codec 增加增量 payload chunk 接口。收到大的 WebSocket 帧时，最多保留受限 header/scratch 和待转发片段，将片段映射到 FetchRPC DATA；禁止先收完整 64 MiB 帧再切成 IPC 小帧。原 Frame API 可以作为小帧测试适配器保留。

`WebSocket.send()` 保持参考的同步返回形状。native 泵可使用 WOULD_BLOCK 和 pending promise，但 JS send 不改成可 await 的新 API。发送队列达到边界时采用在 conformance 中登记的确定异常或关闭策略，同时维护准确的 buffered amount；不承诺“最终阻塞或丢弃”。

## 6 Host 数据路径和出站策略

single-worker、static-pool 和 Linux managed 共享握手校验和 WebSocket session 逻辑。HTTP 状态、routing、CORS 和 admission 的职责不在三个模式中复制。

握手识别先确认 WebSocket Upgrade，再校验 GET、HTTP/1.1、Connection token、Upgrade token、唯一且可解码为 16 字节的 key、版本 13 和 subprotocol 语法。普通 HTTP 上无关的 Sec-WebSocket 字段不触发握手错误。重复 Connection/Upgrade 按 HTTP 字段合并与 token 规则处理，不能遇到重复就返回 kNone 绕开校验。失败在申请 worker request/channel slot 前返回确定 400/426。

101 切换保留 Beast buffer 中已读到的首个 WebSocket frame 字节，串行完成 HTTP handshake 写入后启用 WS 写泵。断连探测从 HTTP 切换为 WS 传输所有权。控制帧的 ping/pong、Close 和取消有独立受限进度，不能被零 DATA credit 饿死，也不能为 ping flood 开无限控制队列。

出站连接由 host dialer 处理，使用 spawn 时保存的 App egress/capability 快照：

1. 验证 ws/wss URL、端口、fragment/credentials 和候选 protocols。
2. 依次执行 hostname 与实际解析地址的策略检查，保留显式 IP/CIDR deny 优先、protected range 和 hostname 授权的既有语义。
3. 连接授权过的解析结果；TLS 执行 CA、hostname/SNI 验证。
4. 验证 101、Upgrade/Connection、Sec-WebSocket-Accept 和选中的 protocol；失败通过 dial ID 返回 REJECT。
5. 将网络消息和 FetchRPC channel 互相泵送，取消时同时停止 resolver、connect、TLS 和 handshake。

初始方案不跟随 WebSocket HTTP redirect；参考 fixture 若证明需支持，应先记录其授权和重新解析规则，再修正协议与测试。禁止复用未经当前授权校验的地址。worker 内的 txiki ws.c、raw socket 和未授权 Binding 模块继续不向 User 开放。

## 7 JS API 和嵌入接口

新增项目自有 `js/websocket.js`，通过 bootstrap 连接受控 native channel，不直接暴露 txiki WebSocket。Response 的 101 扩展只接受当前 pair 的可移交 client endpoint，body 必须为空；已 accept 或已移交的同一端不能再次移交。

先用锁定 workerd 确认：重复 accept、错误使用端点、text/binary 类型、binaryType、send 参数转换、close code/reason、allowHalfOpen、异常事件和 readyState。有效用法为创建 pair、接受 server、在 101 response 中返回 client。same-isolate pair 能力是否保留按差分结果和既有 deviation 决策记录；不能以一个伪 client 对象满足 Object.values 后宣称完整兼容。

公开 C ABI 的新增职责包括：提交 Upgrade 并预留 channel ID、接收升级决定、响应 worker outbound dial、发送消息、授予 credit、half-close、Close 和 Cancel。通道事件沿既有 event pump 排序，使用新增 event kind 与 decoder；decoder 输出 ID、dial ID、owner、u64 credit 和借用 payload，显式 caller_size 保护新结构。

API 签名表必须注明调用方向、有效状态、WOULD_BLOCK 时是否已消费输入、payload 有效期、重入/线程规则，以及失败后是否需 Cancel。首版不扩展既有 capsid_event 的大小。`capsid_worker_upgrade_respond` 草案名称若与 host/worker 实际方向不符，使用上述职责拆分替代并更新契约。

## 8 验证和发布证据

wire grammar、payload decoder、capability gate 和 channel state machine 分层验证。黄金序列包含真正的帧、驱动方向、初始 credit、每一步状态/事件和明确错误，不能把 steps 文案计数当成状态机测试。对照 runner 必须先执行独立绝对断言，再比较两个 runtime 的结果。

0.3.0 发布门禁要求 WS 场景实际注册且执行，禁止 WebSocketPair 尚未公开、缺驱动、exit 77 或 ranNothing 被计作完成。保留一般开发环境的 Linux 特权 skip 说明，正式 Linux production gate 则必须在满足前提的环境执行。

测试覆盖包含：原始 v7 caller、v3/v4 混流、大小协商、拒绝后无资源、多个 dial 乱序完成、超过初始窗口的大消息、fragmentation、slow consumer、控制帧插入、同时 Close、half-close、timeout、断连、shutdown、worker replacement，以及 strict egress/TLS 拒绝。ASan/UBSan、host TSan、v4/state/handshake fuzz 和 live-channel soak 均需实际覆盖新路径。

性能工作分为车道修复和数据重测。车道修复要求：生产姿态显式记录并在发布收集时校验；密度端口在控制层分配；递归进程树采样/清理；worker 覆盖证据；cold/warm 明确标记；双方稳定读；最终验证失败不发布结果。收集器拒绝缺证据、坏摘要、身份冲突和重复 cell，记录每条 lane 的 origin，不能用收集时 HEAD 替代测量二进制 commit。

旧 raw artifacts 保持原样。无法证明来源的旧网页条目标记为不可验证或撤出结论，不能补写假摘要。新的 density、QPS、cold-start 目录都进入 evidence，并由同一发布二进制、同一安静会话生成。静态网页上的内存叙述限定到实际采样窗口和工作负载。

参考事实来源为 [workerd 语义档案](workerd-websocket-semantics.md)、锁定的 [WebSocket 实现](https://github.com/cloudflare/workerd/blob/8f311ae3e3cf3064983f56a6a1c8b7ee33d6b99f/src/workerd/api/web-socket.c%2B%2B)、[API 定义](https://github.com/cloudflare/workerd/blob/8f311ae3e3cf3064983f56a6a1c8b7ee33d6b99f/src/workerd/api/web-socket.h) 和 [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html)。

## 2026-10-14 DNS 与连接生命周期补充

Host 出站不再使用 Asio 的后台系统 `getaddrinfo` 任务。每次查询使用独立的
c-ares channel，在 dialer 的 io_context 中以 10ms 非阻塞 poll 驱动 DNS sockets
和 timeout；取消立即销毁查询 channel、socket 和 timer，已排队的结果回调也
可撤销。新查询读取系统 DNS/hosts 配置，使用 c-ares 的解析语义，不加载 OS
的任意 NSS 模块。服务整体拨号期限继续由协商的 dial_timeout_ms 控制。

`ARES_AI_NOSORT` 必须开启：[c-ares 地址排序](https://c-ares.org/docs/ares_getaddrinfo.html)
会尝试连接返回地址，不能让这些连接先于 resolved sockaddr 的 egress 决策。
查询返回最多 64 个 endpoint；正常路径与之前一样，授权后再连接，TLS 验证与
结果 ACK 屏障保持不变。取消用 [ares_destroy](https://c-ares.org/docs/ares_destroy.html)
收回 DNS 资源，不遗留后台 resolver 任务。此改变没有新的 wire 或公开 ABI。

有 Boost 的 Host networking 新增系统 c-ares >= 1.27 依赖，优先静态 provider，
无 configure-time download 或 blocking resolver fallback。私有生成头固定到
选中的 provider，避免其他依赖的 include prefix 带入不同版本。Linux/macOS/
Windows 的依赖安装说明与已有构建工作流一并更新；改动工作流不代表平台验证
已经执行。Native DNS server override 和阶段 observer 仅供原生 owner/测试，
没有 JS/IPC/config 字段可提供预解析地址或更换 DNS 权威。

[DNS/dialer driver](../tests/test_host_dns_dialer.cc) 使用真实 A/AAAA/NXDOMAIN、
不响应的 DNS、填满的 TCP backlog、暂停 TLS/HTTP 的 peer，分别验证各阶段
Cancel/timeout/stop 和 provisional ACCEPT 取消；保留 owner 超过原期限验证
无迟到结果，检查服务 slots/bytes 与 DNS fd/thread 回收。Linux connect wrapper
验证解析本身未探测返回地址。活跃 session 另测结果 ACK 激活和 Close 期限。

[generation driver](../tests/test_host_channel_lifecycle.cc) 使用真实 worker/网络：
HTTP terminal 后的活跃或 pending standalone channel 继续计入 generation
liveness；retire 拒绝新请求，旧连接仍可收发，新 generation 可以服务请求。
普通 Close、drain deadline、SIGKILL 和 health recycle 都必须关闭旧 socket，
回收预算；replacement 还须重新建立 WS 并成功收发。该 driver 验证共用 pool/
executor 路径，不能替代所有 Managed admin、Binding 或平台端到端场景。

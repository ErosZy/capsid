## 2 P1：code 的 16 位取模引入数值语义回归

[websocket.js](../js/websocket.js) 的 `toUint16()` 同时用于 close 和 CloseEvent。
锁定 workerd 接受 `1000.5` 并不能推导出所有 code 均按无符号 16 位转换。

| 输入 | 锁定 workerd | 当前 Capsid |
| --- | --- | --- |
| `close(66536)` | InvalidAccessError | 接受，截为 1000 |
| `new CloseEvent('x', {code:65537}).code` | 65537 | 1 |
| `close(-64536)` | InvalidAccessError | 接受，截为 1000 |
| `new CloseEvent('x', {code:-1}).code` | -1 | 65535 |
| `close(1000n)` | TypeError | 接受 |
| `new CloseEvent('x', {code:1000n})` | TypeError | 构造成功，code 为 1000 |

前两行在旧实现上已经与 reference 一致，这轮修复使其回归。负数/大数归一化
和 BigInt 转换需要按实际 reference 固定黄金；不要仅根据浏览器 WebIDL 名称
选择转换规则。`Number(BigInt)` 的显式转换也不能代替会拒绝 BigInt 的参数转换。

需同时保留小数修复、非法 code 拒绝、大数与负数 CloseEvent 可观察值及 BigInt
异常的回归，分别核对构造值和实际 wire Close，避免修 C03 时破坏控制输入。

## 3 P1：close 后同步抛错，没有及时产生终态

复现 handler：

```javascript
server.send('a-before');
server.close(1000, 'done');
throw new Error('expected listener error');
```

Reference 丢弃暂存消息并以 1006、wasClean=false 结束；当前 Capsid 没交付消息，
但在 2 秒观察窗口内也没有 close/error，最终由探针主动关闭。

原因来自新的 stage：`close()` 在实际提交前就设 `outgoingClosed=true`；同步
throw 把 stage 标为 abort，`abortFromHandler()` 又因 outgoingClosed 直接
返回。暂存 Close 没提交，transport abort 也没执行。旧 C17 只测 send 后 throw，
因此可以通过而遗漏这个分支。

需区分 JS 已调用 close 与 native Close 已提交/transport 已终止。异常分支不能
仅凭 outgoingClosed 早退。补 send→close→throw、close→throw、多 listener、
暂存发送额度失败后 close 等组合，断言及时终态和 owner/channel/预算归还。
本轮只证实 2 秒内缺终态，没有把它描述为已证明的永久保留。

## 4 P1：Response 构造取消了 WebSocket 类型检查

为修 C14，`Response` 把 endpoint readiness 校验移到 transfer，这是合理的阶段
调整；但 [fetch.js](../js/fetch.js) 现在仅检查 socket 不是 null/undefined，
连类型检查也取消了：

| `new Response(null, {status:101, webSocket:…})` | workerd | Capsid |
| --- | --- | --- |
| `{}` | TypeError | 成功，status 101 |
| `true` | TypeError | 成功，status 101 |
| `1` | TypeError | 成功，status 101 |

这是构造阶段的新回归。构造时应验证 WebSocket 类型，transfer 时再验证
accept/角色/重复移交等状态。不能恢复旧的完整 readiness 检查来撤销 C14 修复，
也不能以实际移交最终会失败代替构造期的兼容行为。

## 5 P1：listener 返回 Promise 的 rejection 仍被当作致命关闭

两种追加场景：async handler 在 send 后立即 reject；send 后 await 80 ms 再 reject。
Reference 两种场景都能继续接收下一条 b 并交付 `b-after`，最后由客户端正常
关闭（1000、wasClean=true）；Capsid 两种都在第一条消息后关闭为 1006、
wasClean=false。

这些是对当前 C17 修复的边界审查，不能将它们全部算为新引入的回归。原方案
要求同步 throw、异步 reject 和多回调矩阵，本轮正式用例仍只钉住同步 throw。
`collector` 等待 listener 返回的 Promise，并由外层 catch 执行 abort，这个
行为不能自动套用到 reference 的 listener 返回值。

需区分事件派发、异步资源 owner 和返回 Promise 的失败处理。补立即 reject、
await 后 reject、send 前后 reject、下一条消息仍可用和最终取消/回收的断言。
C15 的并发派发及原始丢帧根因仍待解决，不通过放弃 owner/GC 记账来修顺序。

另外确认两个转换缺口：CloseEvent reason 为 Symbol 时 reference 抛 TypeError，
Capsid 接受为 `Symbol(s)`；binaryType 为 Symbol 时 reference 抛 TypeError，
Capsid 静默保留 blob。这里属于增补的兼容边界，未声称均由本轮新增。

## 6 P2：失败回滚后旧 Worker 的指标没有恢复

旧 v1 Worker 在三次失败后仍存活并响应，其 PID 为 432937；回滚后指标指向已
退出的新 Worker PID 432958，RSS 为 0，额外等待 1.5 秒后仍如此。初始指标正确
指向 v1，RSS 为 9,801,728 bytes。

`on_worker_started` 在准备期覆盖 active_workers/worker_pid，失败新 pool 退出
时又清掉观察记录；abort 仅恢复路由，没有恢复仍在服务的旧 Worker 的观察身份。
这是失败事务剩余的可观察问题，不将其误报为 Worker 没回收。

需恢复指标对应的 active generation/Worker，补失败后仍服务版本、实际 PID
和指标 PID 的一致性，以及新 Worker 再次成功激活后的观察切换。

## 7 测试稳定性和门禁

独立 70 项唯一失败为 `websocket_outbound_static-pool`，命中 9–12 秒拨号期限
的时间断言，错误/关闭形状断言已通过。随后三次单独复跑均通过。原始失败
没有打印实际 elapsed，因此本轮未认定它来自 CPU 负载、时钟或具体代码回归。
保留 69/70 和三次通过，不能只记录最后一次绿灯。

应记录实际 elapsed 和拨号阶段，使用单调时钟验证期限，并在需要时检查
事件调度/取消完成时点；不要直接放宽时间窗口结束审查。

新增真实 Host persist 失败项确实改善覆盖，但还应确认每次新 Worker 已 READY，
且故障发生在 persist 阶段，避免未来提前失败也被算作回滚通过。当前 chmod
方式还依赖执行用户的文件权限；应使用明确的持久化故障注入条件覆盖不同运行
用户。对象级 factory/pool 释放、最后一次 retire 后不再操作的回收仍待直接断言。

当前注册 412 项，不能把它们称为全部单测或声称已全跑。现有 reference 条件
注册、CI Node `24` 与精确 lock 不一致、缺少锁定 workerd 安装和严格报告比较
的问题仍未修正。新 api-compat 的 C15 分支断言 Capsid 当前串行差距，文档已
承认未修；这项通过只能表示已知行为未变，不能计为强兼容通过。

文档检查通过（40 documents、12 modules）。工作区 `git diff --check` 另发现
`src/worker_runtime.cc:2689` 的现有尾随空格，本轮保留源码不作修改。

## 10 继续审校：C12 真实协议 header 仍不兼容

上轮后运行源码、二进制及 GLM 索引没有新变更，本次继续检查真实握手与移交。
同一受控 TCP peer 回显请求的第一个 protocol，两端分别记录实际 header、
open 时的 `ws.protocol` 和 close。single-worker、static-pool、managed 三种模式
结果一致：

| 构造器 protocols 输入 | workerd 请求 header / 选中协议 | Capsid |
| --- | --- | --- |
| 省略或 undefined | 无 header，protocol null | 相符 |
| null | `null` / `null` | 无 header，protocol null |
| 123 | `123` / `123` | 无 header，protocol null |
| true | `true` / `true` | 无 header，protocol null |
| toString 返回 chat 的普通对象 | `chat` / `chat` | 无 header，protocol null |
| 字符串 chat | `chat` / `chat` | 相符 |
| 数组 chat/super | `chat, super` / `chat` | 相符 |

## 11 继续审校：C14 延迟 accept 与移交失败终态

三种 Host 模式分别使用隔离实例，复测 6 类移交操作及 clone：

| 操作 | workerd | Capsid 三种模式 |
| --- | --- | --- |
| 正常 accept 后返回 101 | 升级、echo、close 1000 | 相符 |
| 先构造 Response，再 accept，最后 return | 升级、echo、close 1000 | 相符 |
| return 后定时 80 ms 再 accept | 升级、echo、close 1000 | 503，无 WebSocket 消息 |
| 返还已 accept 的 endpoint | 已输出 101 后连接结束，记录 TypeError | 8 秒窗口内无响应头，需探针取消 |
| 同一 Response 第一次移交 | 升级、echo、close 1000 | 相符 |
| 同一 Response 第二次跨请求移交 | HTTP 500，记录跨请求 I/O 错误 | 8 秒窗口内无响应头，需探针取消 |
| 带 WebSocket 的 Response.clone() | TypeError | 相符 |

可成功的延迟 accept 输入为：

```javascript
const [client, server] = new WebSocketPair();
server.onmessage = event => server.send(event.data);
const response = new Response(null, { status: 101, webSocket: client });
setTimeout(() => server.accept(), 80);
return response;
```

`validateResponseWebSocket()` 在 transfer 开始要求 peer 已 accepted，这与
reference 支持的延迟 accept 有差异。C14 构造期输入已修，但完整生命周期
尚未完成。按强兼容目标需重审 pending-accept 的 owner、排队、额度和取消；
不能只删除 guard 后在 accept 前派发消息，或无限等待未 accept 的 peer。

非法/重复移交同样需要明确失败终态。Capsid 三模式在 8 秒内均未产生响应头，
日志有校验 TypeError。这里不把它描述为永久挂起，也不要求复制 reference 在
错误 endpoint 上先写 101 的处理；验收应检查错误响应/连接终止及所有资源归还。

证据为索引 `continued_transport_review`：9 个构造/握手输入、6 类移交、clone
在三模式分别执行；省略/undefined、正常字符串/数组、正常移交和 clone 均有
匹配控制。没有重复运行未变源码的完整 70 项集合，本轮只增加上述覆盖。

早期混合场景包含永不 accept 的 peer，reference 清理未收敛；共享 Capsid
实例的后续错误也会受前一场景影响，这两轮保留为诊断。最终结果来自隔离
Host（重复移交保留自己的两请求实例），reference 与所有正式 Host 正常退出，
无 forced stop。建议分别增补协议 header 和 pending-accept/移交失败回归，
并与第 2–8 节的修正及测试清单一并交给 GLM。

# H3 v2 compatibility

## Status

Capsid Runtime validates pinned **H3 2.0.1-rc.26**. The version and integrity are pinned by `examples/h3-v2-reference/package.json` and the lockfile. It does not represent other RCs or future H3 v2 releases.

The reference build produces seven audited ESMs: five entry types, plus malformed URL and debug fixtures. Each output must be a single file with zero external/dynamic imports and no source maps, Node built-ins, `file:`, `require`, platform globals, H3 Node adapter, srvx listener, or server implementation; the size cap is 192 KiB.

## Build and verification

```sh
npm ci --ignore-scripts --prefix vendor/txiki.js
npm ci --ignore-scripts --prefix examples/h3-v2-reference

cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build build --target \
  test-h3-v2-worker-driver test-module-denial test-p0-integration
ctest --test-dir build --output-on-failure \
  -R '^(worker_h3_v2_|worker_p0_contract$)'
```

129 deterministic vectors compare the same bundled H3 application between the Node reference and the real worker, with independent absolute assertions.

## Verified

- H3 app, `{ fetch }`, named/wrapper/standalone handler entries;
- `on`, method shortcuts, `all`, `use`, `register`, `mount`, `fetch`;
- route, params/query, Unicode, malformed URL policy;
- H3Event, request-local context, middleware and hooks;
- JSON/text/urlencoded/multipart/File/ArrayBuffer/stream requests;
- object/string/binary/Blob/File/BigInt/Promise/stream/redirect responses;
- prepared status/status text/header and ordered multiple `Set-Cookie`;
- error redaction, debug stack, hook failure, and worker reuse;
- nested apps, `fromWebHandler`, cookies, CORS, auth, validation, session, cache, proxy, in-memory static, and SSE/EventStream;
- plugin, lazy init, `onDispose`, direct fetch, permission, cancel, timeout;
- 196,645-byte bidirectional stream across multiple 1 KiB FetchRPC credit windows.

The differential compares status/status text, normal headers, ordered `Set-Cookie`, exact body and stream aggregate, route/context/trace, and error/prepared-response behavior. Only dynamic `Date`, generated session values, and transport chunk counts are normalized; cookie attributes/order, total length, and checksum must still be exact.

## Support and exclusions

H3 Core and the runtime-neutral, Web-standard utilities verified above are supported. The host remains responsible for server, pool, timeout, network, and sandbox; "supported" does not mean every unlisted export or option has been verified.

Explicit exclusions:

- `h3/node`, Node handlers/built-ins;
- `serve()`, srvx listener/server;
- `crossws/server` and WebSocket server/upgrade;
- Bun, Deno, Cloudflare, Lambda, and similar adapters;
- real filesystem static serving;
- external/remote/network/`file:` module loading;
- process/worker creation, ambient fs, txiki private API;
- host-backed `event.waitUntil` lifecycle extension.

Eight `h3-v2-excluded` tests maintain these boundaries. H3's `event.waitUntil()` convenience method is explicitly listed as Excluded because the host has no corresponding lifetime hook.

Compatibility work only fixes generic runtime behavior: status text, multiple `Set-Cookie` ordering, and bounded tombstone draining after cancellation. The runtime source adds no H3 names or private shims.

## Upgrade process

After updating the exact dependency and lockfile, rebuild/audit the seven bundles and run the differential, lifecycle, permission, excluded-import, global-surface, P0, and sanitizer matrices. New srvx/rou3 inputs, globals, normalization, and exclusions must be explicitly reviewed.
